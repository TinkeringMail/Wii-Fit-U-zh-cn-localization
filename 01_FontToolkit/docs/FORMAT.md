# 格式规格（全部由真实字节验证过）

只记录**本项目实际用到**的格式。每条都标注了"已验证"的判据，没验证的地方会明确写"未验证"。

---

## 1. Yaz0

```
0x00  'Yaz0'
0x04  u32be   解压后长度
0x08  8 字节  保留（全 0）
0x10  压缩流
```

解压算法（与 QuickBMS `src/unz.c` 的 `decodeYaz0` 一致）：

```
循环: 取 1 个控制字节 code，从 MSB 到 LSB 处理 8 个 token
  bit=1  字面量：紧跟 1 字节
  bit=0  回溯引用：读 2 字节 b1 b2
           dist   = ((b1 & 0x0F) << 8) | b2        ; 注意实际起点是 dstpos-dist-1
           length = b1 >> 4
           length == 0  ->  再读 1 字节，length = byte + 0x12   (最长 273)
           否则          ->  length += 2
           从 dstpos-dist-1 复制 length 字节，允许重叠（RLE）
```

**坑：解压长度合理性校验不能按"9 字节出 8 字节"算。**
最省的 token 是"长引用"：3 字节输入（`b1 b2 len`）产出 `0xFF + 0x12 = 273` 字节，即最大膨胀 **91 倍**。
写成 8/9 会让所有正常文件误报损坏（本项目历史上 51 个文件被误判）。

## 2. jARC

```
0x00  'jARC'
0x04  u32  归档总长
0x08  u32  未知（本项目恒定 0x01402300；读到 0x01000000 一类值时当版本号看）
0x0C  u32  条目数
0x10 + i*16   条目 i:
        +0x00  u32 offset   相对文件起点
        +0x04  u32 size     压缩后长度
        +0x08  u32 name_off 绝对偏移，NUL 结尾的 ASCII 名
        +0x0C  u32 f4       = CRC32(名字，含扩展名)     ← 已实测验证
```

**坑 1：条目之间有不等的对齐填充（0x18~0x2C，甚至 0），必须按 `offset` 定位，禁止用 `size` 累加。**
**坑 2：条目是"逐个压缩"的，不是整个归档压一次。** 每条先试 magic：
`jCMP` 或 `Yaz0` 包装 → 解开得到裸数据（`.jfnt` / `.jlyt` / `.jtex` …）；否则就是裸数据。
写回时必须**逐条**重新包装，否则游戏读不出来。

---

## 3. jCMP

```
0x00  'jCMP'
0x04  u32  文件总长 = 20 + zsize
0x08  u32  flags（常见 0x01010100）
0x0C  u32  zsize
0x10  u32  原始长度
0x14  zlib 流（78 01 …）
```

---

## 4. JFNT

```
0x00  'JFNT'
0x04  ...      flags 等
0x05  u8       flags
0x08  u8       max_w      字宽上限
0x09  u8       height     逻辑字高
0x0A  u8       cols       图集列数
0x0B  u8       pad        字格padding
0x0C  u16      范围数 n
0x0E  范围表   n × 6 字节： u16 start_code | u16 end_code | u16 first_glyph
之后  u16      字形总数 count
之后  count × u8  每个字形的宽度（前进量）
之后  填充 0x00 到 0x80 边界
之后  jIMG（图集）
```

* `cell_w = max_w + pad`，`cell_h = height + pad`。
* 码位→字形号：`glyph = first_glyph + (cp - start_code)`，范围是**连续**的。
* `height` 是**逻辑**高度，可以不是 16 的倍数；真正要 16 对齐的是下面 GTX 的**填充**高度。

---

## 5. jIMG / Gtx2 / BLK

```
jIMG + 0x10  u32  GTX 偏移（取低 16 位）
jIMG + 0x14  u32  GTX 长度
jIMG + 0x1C  u32  CRC32(整个 jIMG，计算时 0x1C..0x24 先置 0)
jIMG + 0x20  u32  CRC32(文件名去扩展名)          ← 必须保留原值
GTX   + 0x04 u32  第一个 BLK 的偏移
BLK 头 0x20 字节： 'BLK{' | u32 头长 | ... | u32 类型 | u32 数据长 | ...
      类型 0x0B = 表面描述（16 个 u32 顺排）
      类型 0x0C = 像素数据
表面 [1]=宽 [2]=高 [5]&0xFF=格式（0x35 = BC5） [8]=imageSize [12]=tileMode [15]=pitch(字节/块行)
```

* `imageSize` 必须能被 **32768** 整除（= 32×16 宏块 × 64 B），即块行数必须是 **16 的倍数**。
* `0x0B` 里还有一个低 13 位 = (高 − 1) 的字段，改了高度必须同步改它。
* 像素是 BC5（两个 BC4 通道：`ch0` 填充、`ch1` 描边）。`ch1 = ch0 膨胀 r=3`（实测 IoU 0.98）。

---

## 6. tileMode4 寻址（这是最容易解错的一步）

像素按 4×4 块线性化，再按 **32×16 块 = 512 块**的宏块重排：

```
宏块号  mt = (xb >> 5) + (pitch_blocks >> 5) * (yb >> 4)
块内号  n  = bits 依序拼： y0, x0, x1, x2,
                           x3^y3, x3^y5, x4^y4,
                           y1, y2
地址    addr = mt * 512 + n        （单位：16 字节/块）
```

* `pitch_blocks = pitch / 16`（一"块行"占 pitch 字节）。
* 同一公式可用于读和写；写入时只需重编码被改动的块，块外像素原值保留。

## 7. 八个必须知道的坑（每条都踩过）

1. **Yaz0 校验上界**：91×，不是 8/9。（踩过：51 个文件被误判损坏）
2. **jARC 条目有对齐填充**：读 offset，不读 size 累加。（踩过：解出半截文件）
3. **jARC 条目逐个压缩**：整体压缩会导致游戏读不出条目。（踩过：改完进游戏黑屏）
4. **`f4` 是名字的 CRC32**：重建时必须重算，不是随机值。
5. **图集高度/块行要对齐 16（=64 像素）**：不对齐时 GPU 按宏块读到错位数据，表现为"某些功能死机"。
6. **`cell_w/h` 常常不是 4 的倍数**（`DB_3_S` 是 39×55）：所以不能"整块搬字形"，只能解码块 → 改格内像素 → 重编码块。
7. **`height` 存逻辑高，`imageSize` 存填充面积**：两者是两套坐标，写反了会导致 `--verify` 报"高度不对"或图集越界。
8. **标定取样必须是汉字**：按码位排序取前 12 个会取到 `!"#$%` 这类稀疏字符，量出来的"原版墨水率"是标点的，不是汉字的（本项目曾因此得出"DB_L_3 是细体、需要换字重"的错误结论，实际 58.6% 墨水率、75 SemiBold 正好）。

---

## 8. 未验证 / 需要时再查的部分

* `jIMG` 头里 0x00–0x0F 各字段的确切含义（本项目只读写 0x10/0x14/0x1C/0x20）。
* `BLK 0x0B` 中除 宽/高/格式/imageSize/tile/pitch 之外的字段（按原值搬运，不解释）。
* 其他压缩格式（`Gfx2` 里的 `0x36`/`0x37` 等）未处理 —— 本项目只遇到 BC5。
* `jARC` 的 `0x08` 字段在不同归档里是否为版本号，尚未交叉验证；本项目按"读原值写回原值"处理，最安全。
