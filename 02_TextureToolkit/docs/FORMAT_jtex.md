# Wii Fit U 贴图资源格式规格（jCMP / jARC / jIMG / GTX / BC）

> 本文件是 `WiiFitU_TextureToolkit` 的底层依据。所有数字都来自对
> `update\content\ui\*.jarc` 与 `ui\aot_tex.jarc` 的**实测**，不是推测。
> 若你改用别的工具，也必须遵守这里的规则，否则游戏会拒绝读取或花屏。

---

## 0. 层级总览

```
xxx.jarc
 └─ jCMP（zlib 压缩外壳，可有可无）
     └─ jARC（归档：条目表 + 名字块 + 数据区）
         ├─ 条目 1：jIMG（贴图）        <- 绝大多数 ui 贴图包属于这一类
         ├─ 条目 2：jMDL（模型，内含 1~N 个 jIMG）
         └─ 条目 3：jarc（嵌套，如 ui_fb_tex.jarc 的 60 个条目全是 jarc）
             jIMG
              └─ GTX 块链
                  ├─ BLK 0x0B  surface（尺寸/格式/pitch）
                  ├─ BLK 0x02  aux（元数据，原样保留）
                  ├─ BLK 0x0C  像素数据（mip0）
                  └─ BLK 0x0D  mip 数据（部分资源才有）
```

本项目 5 个归档的实测头部：

| 归档 | 文件大小 | 外层 | 内层大小 | `jARC.unknown` | 条目 |
| --- | ---: | --- | ---: | --- | ---: |
| `update\content\ui\mme_us_eng_tex.jarc` | 688,743 | jCMP | 2,446,080 | `0x01402300` | 16 |
| `update\content\ui\mme_eu_eng_tex.jarc` | 689,144 | jCMP | 2,446,080 | `0x01402300` | 16 |
| `update\content\ui\models_data.jarc` | 10,085,881 | jCMP | 23,072,604 | `0x01200300` | 497 |
| `update\content\ui\ui_fb_tex.jarc` | 18,281,157 | **无**（裸 jARC） | 18,281,157 | `0x01200100` | 60 |
| `ui\aot_tex.jarc`（本体） | 1,668,635 | jCMP | 4,553,088 | `0x01402300` | 50 |

## 1. jCMP（压缩外壳）

```
0x00  'jCMP'
0x04  u32  文件总长        = 20 + zsize
0x08  u32  flags           实测 0x01010100；低字节是 zlib 压缩级别
0x0C  u32  zsize           压缩流字节数
0x10  u32  rawsize         解压后字节数
0x14  zlib 流             长度 zsize
```

规则：

- **重压时保留原 flags**，游戏不校验压缩级别。用 zlib level 9 体积更小
  （`mme_us_eng_tex.jarc` 从 688,743 降到约 582 KB，无副作用）。
- `rawsize` 必须等于解压后的真实长度，写错游戏会读到截断数据。
- 判断有没有外壳只看前 4 字节：`ui_fb_tex.jarc` 就是裸 jARC。

## 2. jARC（归档）

```
0x00  'jARC'
0x04  u32  文件总长
0x08  u32  unknown        每个包不同，必须原样保留（见上表 3 种取值）
0x0C  u32  条目数 N
0x10  条目表，每条 16 字节：
        +0  u32  数据偏移（相对 jARC 起点）
        +4  u32  数据长度
        +8  u32  名字偏移（指向名字块内的 'name\0'）
        +12 u32  f4 = CRC32(文件名去后缀)
...   名字块：按条目顺序连续写 "name\0"
...   补 0 到「数据区起点」的 align 边界
...   数据区：条目数据；**条目之间**按 align 补 0
       ⚠️ 最后一个条目之后不补齐，直接 EOF
```

### 2.1 `unknown` 字段

三种取值都出现过：`0x01402300`、`0x01200300`、`0x01200100`。
它不是版本号也不是标志位集合，**没有推导出来的生成规则**，
唯一正确的做法是**从原文件读出来再写回去**。

### 2.2 对齐值 align

- 每个包不同：`mme_*` = `0x10`，`ui_fb_tex` = `0x20`，`tml_tex`（内层）= `0x10`。
- 不能猜。`putback.py` / `nestput.py` 的做法是：
  用原始 blob 重建 → 与磁盘文件逐字节比对 → 遍历候选 align，找到
  能产出**完全一致**结果的那个。输出 `对齐推断: 0x10  重建与原件完全一致 ✓`，
  这一行是后续一切操作的可信前提。

### 2.3 最后一条不补齐（本项目最容易踩的坑）

实测：`ui_fb_tex.jarc` 若给最后一个条目也补对齐，重建结果与原件差 **+27 字节**，
首个差异在 `0x7`（总长字段）。修正后三个归档全部 `重建与原件完全一致 ✓`。

## 3. jIMG（贴图条目）

```
0x00  'jIMG'
0x04  u32  文件总长
0x08  u16  宽
0x0A  u16  高
0x10  u32  GTX 偏移（低 16 位有效，本项目样本都是 0x80）
0x14  u32  GTX 长度
0x1C  u32  CRC32(整个文件)，计算前把 0x1C..0x24 这 8 字节置零
0x20  u32  CRC32(文件名去后缀，UTF-8)
```

**改完像素必须重算这两处**，否则可能被游戏拒绝（表现为白块或直接不显示）。
实测成立的例子：

| 名称 | CRC32(名称) | 文件 0x20 字段 |
| --- | --- | --- |
| `tml_stamp_pic001_us_frn` | `0x024151D7` | `0x024151D7` ✓ |
| `tml_stamp_pic001_us_eng` | `0x9FAC0A77` | `0x9FAC0A77` ✓ |
| `plz_button001_001` | `0x0F9527AA` | `0x0F9527AA` ✓ |

注意第 2 行：**改名字就必须改 0x20**。所以「把 frn 的印章改名成 eng」
不能只 `copy`，必须走 `copyjtex.py`（它同时重算 0x1C 与 0x20）。

### 3.1 jMDL 里的贴图

`models_data.jarc` 的条目是 `jMDL`，一个 jMDL 里可以有多个 jIMG。
实测 `training_obj001_txt_us_eng.jmdl`（62,848 B）：

```
jIMG @0x780  45,312 B   256x64  BC3   <- 文字牌匾，要改
jIMG @0xB880 15,616 B    64x16  BC1   <- 装饰，跳过
```

所以按后缀处理时不能只看「一个文件一张图」，要逐 jIMG 判断尺寸。

## 4. GTX 块链

```
GTX 起点 go = jIMG + 0x10 里的低 16 位值
  go+0x00  'Gfx2'
  go+0x04  u32  头长度（本项目都是 0x20）= 第一个块的位置

块头 0x20 字节：
  'BLK{' | u32 头长度 | 2×u32 | u32 类型 | u32 数据长度 | 2×u32
  下一个块 = 当前块 + 头长度 + 数据长度
```

类型：

| 类型 | 含义 | 说明 |
| --- | --- | --- |
| `0x0B` | surface | 16 个 u32，尺寸/格式/pitch 都在这里 |
| `0x02` | aux | 元数据，长度随资源不同，**原样保留** |
| `0x0C` | 像素数据 | mip0，要改的就是这一块 |
| `0x0D` | mip 数据 | 只有部分资源有 |
| `0x01` | 结束 | 数据长度为 0 |

### 4.1 四个真实样本的块链

```
bck_obj_txt_us_eng.jtex   24,832 B  GTX@0x80
   surf 156 | aux 7,908 | pixel 16,384 | end
mme_panel001_pic_tst_us_eng.jtex 106,752 B
   surf 156 | aux 3,812 | pixel 102,400 | end
tml_stamp_pic001_us_eng.jtex 73,984 B
   surf 156 | aux 7,908 | pixel 65,536 | end
training_obj001_txt_us_eng.jmdl（内层 jIMG @0x780）45,312 B
   surf 156 | aux 7,908 | pixel 16,384 | aux 8,128 | mip 12,288 | end
```

只有牌匾那个 jMDL 带独立 `0x0D` mip 块，这解释了为什么它是唯一
「远处可能切到旧图」的类型（见 §7）。

### 4.2 定位像素块的经典写错法

```python
pos = u32(g, go + 4)        # ❌ 这是「相对 GTX 起点」的长度，不是 jIMG 内偏移
pos = go + u32(g, go + 4)   # ✅
```

症状：`[错误] 未找到像素块`。本项目三个工具都栽过这一处。

### 4.3 surface 块的 16 个字段

`dim, width, height, depth, numMips, format, aa, use, imageSize, imagePtr,
mipSize, mipPtr, tileMode, swizzle, alignment, pitch`

实测：

| 样本 | 尺寸 | 格式 | imageSize | pitch | tileMode | alignment | numMips |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| 按钮 | 256×64 | BC3 | 16,384 | 64 | 4 | 8192 | 1 |
| 面板 | 548×308 | BC1 | 102,400 | 160 | 4 | 4096 | 1 |
| 印章 | 256×256 | BC3 | 65,536 | 64 | 4 | 8192 | 1 |
| 牌匾 | 256×64 | BC3 | 16,384 | 64 | 4 | 8192 | 1 |

`swizzle` 四个样本都是 `851968`（`0x000D0000`），`dim=1`、`depth=1`。

## 5. 像素格式

| 格式码 | 名称 | 每单元字节 | 单元含义 |
| --- | --- | ---: | --- |
| `0x1A` | RGBA8 | 4 | 1 像素 |
| `0x31` | BC1 (DXT1) | 8 | 4×4 块 |
| `0x32` | BC2 | 16 | 4×4 块 |
| `0x33` | BC3 | 16 | 4×4 块 |
| `0x34` | BC4 | 8 | 4×4 块（单通道） |
| `0x35` | BC5 | 16 | 4×4 块（两通道） |

**BC3 的字节顺序**：前 8 字节是 alpha（按 BC4 解），后 8 字节才是颜色（按 BC1 解）。
搞反画面会变成噪点。

本项目实际出现的只有 `0x33`（文字/印章）和 `0x31`（面板截图）。
`0x32/0x34/0x35/RGBA8` 的解码器已实现（`jt8.py`），但**本作未遇到**，未经实机验证。

## 6. tileMode 4（2D_TILED_THIN1）—— 最难的一步

坐标 `x, y` 的单位是**「单元」**，即上表的 4/8/16 字节格：

- RGBA8：单元 = 1 像素
- BC1 / BC3 / BC5：单元 = 1 个 4×4 块

```
mt = (x // 32) + (pitch // 32) * (y // 16)
addr = mt * 512 + index          // index 单位 = 单元，乘单元字节数得到字节偏移
```

`index` 的位序（`^` 是异或，`x0` 表示 x 的最低位）：

```
4B  (RGBA8) ：[x0, x1, y0, x2, y1, y2, x3^y3, x3^y5, x4^y4]
8B  (BC1)   ：[x0, y0, x1, x2, y1, x3^y3, x3^y5, x4^y4, y2]
16B (BC3/BC5)：[y0, x0, x1, x2, x3^y3, x3^y5, x4^y4, y1, y2]
```

其中 `x0..x4`、`y0..y5` 是坐标的二进制位（低位在前）。

### 6.1 pitch 与 rows 必须按 32/16 向上取整

这是文档里最容易写错的一处，实测结果如下：

```
pitch = ceil(块宽, 32)        // 548 像素 = 137 块 -> 160
rows  = ceil(块高, 16)        // 308 像素 =  77 块 ->  80
imageSize = pitch * rows * 单元字节
```

验算：`160 × 80 × 8 = 102,400` = surface 的 `imageSize` ✓

> 常见错误写法 `160 × 77 × 8 = 98,560`。**少算了 3,840 字节**，
> 因为 macrotile 是 32×16 单元，两个方向都要补齐。

其它样本：256×64 BC3 → `64 × 16 × 16 = 16,384` ✓；
256×256 BC3 → `64 × 64 × 16 = 65,536` ✓。

## 7. 定长压缩 = 体积不会变（整套方案的基石）

BC1 每 4×4 块恒 8 字节，BC3 恒 16 字节，**与图片内容无关**。所以：

> 任何 548×308 的图片，编码成 BC1 后都是 102,400 字节。
> 任何 256×64 的图片，编码成 BC3 后都是 16,384 字节。

推论：

- 整图替换**不改变条目长度** → jARC 内部零位移 → 回封走
  `[A] jARC 内原地覆盖`，条目表一个字段都不用改，这是最安全的路径。
- 如果某次输出报告「长度变了」，说明编码器写错了尺寸或格式，
  **不要继续回封**。

## 8. mipmap 的现实取舍

`bctext.py` / `replacepic.py` **只重写 mip0**。

- UI 元素（广场按钮、印章、面板）按 1:1 绘制，只用 mip0 → 无影响，已实测
- 3D 物体（`training_obj001_txt_*` 牌匾）带独立 `0x0D` mip 块（12,288 B）→
  理论上远处会切到 mip1+ 显示旧图，**但实测正常**

若将来真的发现远处闪回英文，做法是：对新图逐级 box 降采样，
每级按自身尺寸重新做 tileMode4 排布，写回 `0x0D` 块。

## 9. 六个必须记住的坑（按踩坑次数排序）

| # | 坑 | 症状 | 规则 |
| --- | --- | --- | --- |
| 1 | jARC 重建给最后一条补齐 | `对齐推断 不完全一致，长度差 -3420 / -501 / +27` | 条目之间补，最后一条不补 |
| 2 | 像素块偏移没叠加 GTX 起点 | `[错误] 未找到像素块` | `pos = go + u32(g, go+4)` |
| 3 | 用 `--dry` / `--report` 测写入 | 预览正常，正式跑就崩 | 新写的「读-改-写」脚本先单文件真写一次 |
| 4 | 配色判定按像素数量 | 填充/描边反了，字变成绿底黄字 | 按**边界接触率**判：最高 = 描边，接近 0 = 填充 |
| 5 | 用坏掉的打包器回封 | 游戏读不到 / 花屏 | `jarcx.py` 只用于解包，回封只用 `putback.py` / `nestput.py` |
| 6 | 回封基准用错版本 | 之前改好的条目被冲回英文 | 返工时基准必须换成「已部署版本」 |

第 3 条在本项目出现过三次，全部是同一类错误：

- `putback.py`：`struct.pack(">III", ...)` 传了 4 个值
- `bctext.py`：像素块偏移基准错（即坑 2）
- `replacepic.py`：`raw = path.read_bytes()` 少了 `bytearray()`

诊断路径在「写入分支之前」就 `return` 了，所以 `--dry` 永远踩不到写入代码。
